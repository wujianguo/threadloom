# NestJS Express: Better Auth and Mastra adapter compatibility

Researched 2026-11-09 for [验证 NestJS 中 Better Auth 与 Mastra 适配器能否共存](https://github.com/wujianguo/threadloom/issues/4). This is a documentation and package metadata assessment, not a running integration. The repository has NestJS 12.4.0, `@nestjs/platform-express` 12.4.0, and Express 5.3.0 in its lockfile; none of the three integration packages is installed ([API manifest](../../apps/api/package.json), [lockfile](../../pnpm-lock.yaml)).

## Conclusion and proposed version set

**Yes, conditionally.** The published package constraints admit a single Nest Express process. Select a shared application-owned Better Auth instance, mount its handler at `/api/auth`, and pass that same instance to `MastraAuthBetterAuth` in `Mastra.server.auth`. Register `MastraModule` last with a dedicated prefix such as `/api/mastra`. Disable the community module's global guard and deliberately guard ordinary business controllers; let Mastra's own server auth protect its routes. This is the clearest configuration for avoiding two independent guards on Mastra's catch-all controller. The adapter and auth provider docs document these options, but no combined end-to-end test is published or run here. [Better Auth Nest module](https://github.com/thallesp/nestjs-better-auth/blob/master/README.md), [Mastra Nest adapter](https://mastra.ai/reference/server/nestjs-adapter), [Mastra Better Auth reference](https://mastra.ai/reference/auth/better-auth)

## Routing, body parsing, and guards

1. Create Nest on the Express platform with `bodyParser: false`. The community module then skips parsing for its Better Auth base path and applies Express JSON and URL-encoded parsers to other routes. `rawBody: true` on `NestFactory.create` has no effect in this setup; configure the module's `bodyParser.rawBody` if needed. Its handler checks path equality or a slash-delimited child path and passes unrelated requests onward. [Community README](https://github.com/thallesp/nestjs-better-auth/blob/master/README.md), [handler and parser documentation](https://github.com/thallesp/nestjs-better-auth/blob/master/_autodocs/endpoints.md)
2. Keep Better Auth's default `/api/auth` base path; do not apply a Nest global prefix that silently changes one adapter but not the other. Register `MastraModule.register({ mastra, prefix: '/api/mastra' })` after ordinary modules. It uses an `@All('*')` catch-all controller, and Mastra's default API prefix is `/api`; registering it first risks unrelated route interception. The Mastra prefix changes its built-in API routes, while operational `/health`, `/ready`, and `/info` remain unprefixed and custom routes are not necessarily prefixed. Plan collisions and exposure explicitly. [Mastra Nest adapter](https://mastra.ai/reference/server/nestjs-adapter), [server adapter guide](https://mastra.ai/docs/server/server-adapters)
3. `AuthModule.forRoot` installs an `APP_GUARD` by default on non-auth Nest routes. Use `disableGlobalAuthGuard: true` for the proposed split and attach the community `AuthGuard` or application guards to business controllers. The Better Auth middleware handles `/api/auth/*` before Nest guards; Mastra's adapter runs its configured `server.auth` unless `auth.enabled: false`. Disabling the global guard is a design recommendation to keep the Mastra HTTP auth boundary independently testable, not a requirement documented by either project. [Community module API](https://github.com/thallesp/nestjs-better-auth/blob/master/_autodocs/api-reference/auth-module.md), [endpoint behavior](https://github.com/thallesp/nestjs-better-auth/blob/master/_autodocs/endpoints.md), [Mastra Nest adapter](https://mastra.ai/reference/server/nestjs-adapter)

## Session transport and protection

- Pass the **same Better Auth instance** to the Nest module and `new MastraAuthBetterAuth({ auth })`, then set that provider at `new Mastra({ server: { auth: ... } })`. The Mastra provider verifies sessions with Better Auth's `auth.api.getSession`; the Better Auth handler must still be mounted to create sessions. [Mastra Better Auth guide](https://mastra.ai/integrations/auth/better-auth), [provider source](https://github.com/mastra-ai/mastra/blob/main/auth/better-auth/src/index.ts)
- Browser requests need the Better Auth session cookie. For cross-origin Web → API requests, send `credentials: 'include'`, allow the exact Web origin with credentials, and choose cookie SameSite/domain settings for the deployed origins. CORS alone cannot make an ineligible cookie travel. The actual deployment topology remains a separate map decision. [Mastra Better Auth guide](https://mastra.ai/integrations/auth/better-auth), [Better Auth cookies](https://www.better-auth.com/docs/concepts/cookies)
- The Mastra provider accepts Cookie sessions and `Authorization: Bearer` session tokens. Its source copies the Cookie header and converts a bearer token, including a raw unsigned Better Auth session token, into a signed session cookie before `getSession`. Better Auth's bearer plugin is useful for native clients because it exposes a `set-auth-token` response header on sign-in and accepts a Bearer token for Better Auth endpoints. Choose mobile storage and lifecycle after selecting the mobile framework; never assume a browser cookie jar on native clients. [Mastra provider source](https://github.com/mastra-ai/mastra/blob/main/auth/better-auth/src/index.ts), [Better Auth bearer plugin](https://www.better-auth.com/docs/plugins/bearer)
- `MastraAuthBetterAuth` allows any valid logged-in session by default; `authorizeUser` adds an application-wide check. It does not determine per-agent, per-tool, or per-user data access. Explicit `public` and `protected` patterns exist. The current [integration guide](https://mastra.ai/integrations/auth/better-auth) says unmatched paths are protected, while the [class reference](https://mastra.ai/reference/auth/better-auth) says `/api/*` and authenticated custom routes are protected by default and other paths are public. Treat that discrepancy as unresolved until verified against the pinned runtime; explicitly protect the intended API surface and test anonymous access. A `public` match normally wins over a `protected` match. [Mastra class reference](https://mastra.ai/reference/auth/better-auth)
- Nest business controllers are outside Mastra's `server.auth` boundary. They need their own guard/session checks when the community global guard is disabled. Better Auth's origin and CSRF checks on its handler do not automatically secure custom state-changing Nest endpoints. [Community module API](https://github.com/thallesp/nestjs-better-auth/blob/master/_autodocs/api-reference/auth-module.md), [Better Auth security](https://www.better-auth.com/docs/reference/security)

## Streams and mobile implications

The Nest adapter exposes `streamOptions` including redaction and heartbeat configuration, and documents an auth pipeline for bearer tokens, cookies, session refresh, and resource mapping. Mastra's server adapter contracts support SSE (`text/event-stream`) and record-separated streaming, and its Hono implementation handles request abort and emits a final SSE marker. This supports a streaming design in Nest Express, but does **not** prove the combined Nest adapter preserves those semantics through the app's middleware, guards, reverse proxy, or mobile HTTP stack. Test first-byte latency, chunk boundaries, completion, abort, authorization failure before stream headers, and idle/proxy timeouts with the chosen pinned versions. [Nest adapter](https://mastra.ai/reference/server/nestjs-adapter), [server adapter guide](https://mastra.ai/docs/server/custom-adapters), [Hono stream implementation](https://github.com/mastra-ai/mastra/blob/main/server-adapters/hono/src/index.ts)

For future mobile clients, the same Nest API can accept a bearer session token; the Better Auth bearer plugin gives a way to obtain it at sign-in. That is an API capability, not a final mobile session-storage decision. Mobile must handle token persistence and revocation, streamed response reading and cancellation, network changes, and optional cookie-based transport according to its eventual framework. [Better Auth bearer plugin](https://www.better-auth.com/docs/plugins/bearer), [Mastra Better Auth guide](https://mastra.ai/integrations/auth/better-auth)

## Implementation-time proof required

With the exact pins above and the selected database, build one Nest process and verify: `/api/auth/sign-in/email` with an unparsed body; a normal JSON business route; no `/api/auth`/Mastra route collision; anonymous 401 on a protected Mastra agent route; valid browser cookie and native bearer access; revoked/invalid token rejection; ordinary business guard behavior; and a long streaming call with clean abort. This test is the remaining proof needed before calling the coexistence safe in production. [Community handler behavior](https://github.com/thallesp/nestjs-better-auth/blob/master/_autodocs/endpoints.md), [Mastra Nest adapter](https://mastra.ai/reference/server/nestjs-adapter), [Mastra Better Auth guide](https://mastra.ai/integrations/auth/better-auth)
